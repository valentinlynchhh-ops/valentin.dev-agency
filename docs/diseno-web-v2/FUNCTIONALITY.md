# Funcionalidad y producción

## Navegación y rutas

Una landing continua con `#inicio`, `#proyectos`, `#contacto`, `#sobre-mi`, `#vendedores`, `#footer`. Header con Proyectos → `#proyectos`, Sobre mí → `#sobre-mi`, Hablemos → `#contacto`. Servicios → abrir/dirigir al contenido real de especialidades/proceso en contacto o una ruta de servicios existente; Recursos → ruta existente con contenido real, o un pequeño panel accesible con recursos verdaderamente útiles y existentes (por ejemplo links a trabajos públicos). Si no hay contenido, omitir temporalmente ese ítem en producción; mantener el espacio equilibrado, no link muerto. No añadir una séptima sección visual que contradiga el orden aprobado. CTA “Cómo trabajo” → diálogo o contenido expandible con 3 pasos propuestos: entender el objetivo, acordar propuesta/alcance, diseñar y desarrollar; validar condiciones particulares antes de prometerlas. Menú hamburguesa móvil, cerrado por defecto; drawer accesible, Escape, devolución de foco, aria-expanded y cierre al seleccionar. No mostrar el sidebar de escritorio abierto. Header puede quedar sticky después del hero si no tapa contenido; usar scroll-margin-top en destinos. Volver arriba mediante enlace a `#inicio`.

## Portfolio

Cargar datos de una sola fuente. Normalizar URLs y deduplicar. Cinco visibles en pantalla amplia, 2–3 tablet, 1+peek móvil. Controles accionables por teclado y touch, nombres accesibles, estado actual no dependiente del color. Si no hay más de cinco elementos y no hay desplazamiento, ocultar/desactivar controles o implementar rotación real sin duplicados accesibles. Preferir carrusel sin autoplay. Previews reales optimizadas, tamaño reservado, alt descriptivo; no mostrar capturas generadas del mockup como si fueran sitios actuales. Link real para cada tarjeta; rel noopener si abre nueva pestaña. No hacer scraping de datos privados, no acceder detrás de login; screenshots solo de proyectos autorizados. Registrar fallos de URL y asset. Los cuatro dominios proporcionados por el usuario y Estudio Saucedo forman el set inicial; verificar navegación/autoría de adicionales antes de publicar. No afirmar que se capturaron si no se hizo.

## Contacto y reserva

Un flujo central desde los tres CTAs principales. Inspeccionar si ya existe calendario (Cal.com, Calendly, Google Calendar, integración propia), formulario, CRM o backend. Reutilizarlo. Mostrar horarios únicamente desde disponibilidad auténtica. Seleccionar fecha/slot, confirmar zona horaria (usar America/Argentina/Buenos_Aires como default configurable), datos mínimos necesarios: nombre, email y breve objetivo; teléfono opcional si hace falta. Enviar con acción explícita, validación cliente y servidor, proteger de spam con rate-limit/honeypot según arquitectura. Evitar doble submit. Estados: inicial, cargando, sin disponibilidad, error recuperable, conflicto de slot, confirmación real. No mostrar confirmación si no hay respuesta exitosa de backend. Si el slot se perdió, refrescar disponibilidad y avisar. Guardar solo datos necesarios, incluir aviso de privacidad real si se recopilan datos. Nunca exponer API keys o credenciales en frontend.

Fallback sin integración: permitir solicitud de reunión a un email/WhatsApp efectivamente confirmado o un formulario real de la app, no inventar fechas. Diferenciar “solicitar” de “reservar”; no abrir un enlace inexistente. Si no hay ningún canal confirmado, informar en la preview de desarrollo y en el reporte como bloqueo de publicación, no simular funcionalidad. Los datos impresos en la captura no están confirmados; revisar config y fuentes autorizadas del repositorio antes de usarlos. Contacto social abre los perfiles exactos configurados, no las homepages de redes.

## Vendedores

“Quiero sumarme” abre un formulario de postulación real o un canal confirmado. Campos mínimos: nombre, email/WhatsApp, breve experiencia comercial o por qué le interesa, consentimiento/aviso sobre uso de los datos cuando corresponda. No solicitar datos financieros o documentos personales en esta instancia. No prometer contratación, sueldo ni comisiones específicas. “Cómo funciona” abre un diálogo accesible con el proceso comercial y términos que se definirán antes de comenzar. Si hay programa real, mostrar sus condiciones autorizadas; no reutilizar porcentajes de proyectos anteriores automáticamente. Enviar al backend o CRM existente con estados reales. Sin backend ni canal, bloquear el envío de forma transparente y registrar pendiente. No dejar datos personales de terceros, rankings o cifras generadas visibles en producción.

## Accesibilidad, SEO, performance

HTML semántico y una sola H1; h2 por sección, nav/footer landmarks, skip link, labels y mensajes de error vinculados, focus visible (2 px con contraste), objetivos táctiles de al menos 44×44 px cuando sea viable. Modal con foco inicial, Escape, cierre explícito y devolución de foco; no bloquear el uso con teclado. Imágenes decorativas con alt vacío; logo con texto accesible. Respetar reduced motion y pausa manual. Texto y CTA accesibles sin animaciones. Contraste WCAG AA objetivo: 4.5:1 texto normal, 3:1 texto grande y controles donde corresponda. No depender de brillo para leer.

Metadata propuesta: title “valentin.dev — Diseño y desarrollo digital”; description “Diseño y desarrollo sitios web y productos digitales. Estrategia, diseño y tecnología, directamente conmigo.” Idioma es-AR, favicon derivado, Open Graph con imagen propia optimizada. Canonical solo confirmar al configurar dominio final; no asumir que valentin.dev está registrado. No inventar schema de organización, rating ni reviews. No indexar ambientes de preview. Analytics opcional solo si hay integración/consentimiento aplicable; eventos útiles: `project_open`, `contact_start`, `booking_success`, `sales_apply_start`, `sales_apply_success`; no registrar contenido de formularios ni datos sensibles.

No agregar dependencias masivas para efectos sencillos; cargar imágenes bajo fold de forma diferida, dimensiones explícitas, optimizar LCP y fuentes. Objetivos de referencia: LCP <=2.5 s, INP <=200 ms y CLS <=0.1 en mediciones de campo cuando existan, sin prometer cifras sin medición. Revisar errores de consola, requests fallidos, imágenes rotas, layout shift y scroll en móvil. Preservar scripts, endpoints, permisos y estado del proyecto original.

## Deployment Vercel

Identificar framework y configuración existentes, build command, output, Node, env por nombre, integración git y dominio del proyecto. Verificar build local y preview. No crear un proyecto paralelo si ya existe el correcto. No cambiar DNS ni publicar producción sin autorización explícita. Si se necesita acción del usuario, indicar los nombres de variables y pasos, nunca pedir que pegue secretos en archivos compartidos. Si no hay acceso a Vercel, dejar instrucciones concretas. Una vez autorizado, verificar URL final con GET y los flujos reales sin generar solicitudes de clientes de prueba en producción sin permiso. Registrar deployment real solo si se ejecutó.
